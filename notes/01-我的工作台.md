## 三、先建立一条整体主线

一次网页访问可以先简化为：

```text
用户输入 URL 或点击页面按钮
            ↓
浏览器或网页脚本确定目标 URL 和 HTTP 方法
            ↓
浏览器发出 HTTP/HTTPS 请求
            ↓
请求经过 Burp，被记录或拦截
            ↓
服务器处理请求并返回响应
            ↓
浏览器接收响应，显示页面或更新页面内容
```

这里涉及的角色不同：

- 浏览器：发送请求、接收响应、显示网页、运行网页脚本。
- 网页：浏览器加载并运行的一组页面资源。
- 服务器：接收请求、处理业务并返回结果。
- Burp：位于浏览器和服务器之间，观察和修改通信内容。

## 四、浏览器、网页和网站

### 1. 浏览器

浏览器是运行在本机上的软件，例如 Chrome、Edge 和 Chromium。

它主要负责：

- 根据 URL 发送请求；
- 接收服务器响应；
- 解析并显示 HTML、CSS；
- 运行 JavaScript；
- 管理 Cookie、缓存等信息。

### 2. 网页

网页是浏览器从服务器取得资源后，解析、显示并运行出来的页面。

常见资源包括：

| 资源 | 作用 |
|---|---|
| HTML | 描述文字、按钮、输入框等结构 |
| CSS | 控制颜色、大小、位置和排版 |
| JavaScript | 控制交互，并通过浏览器发送后台请求 |
| 图片等资源 | 提供页面需要展示的内容 |

网页通常借助浏览器进行网络通信，而不是自己直接建立网络连接。

### 3. 网站

网站是业务和产品上的概念，通常由多个网页、接口和静态资源共同组成。
网站和“源”不是完全等价的概念，一个网站可以跨多个源。

## 五、URL、源和 HTTP 方法

### 1. URL 是什么

URL 是具体资源的地址，例如：

```text
https://www.example.com:443/user/profile?id=100#basic
```

可以拆成：

| 部分 | 内容 |
|---|---|
| 协议 | `https` |
| 主机名 | `www.example.com` |
| 端口 | `443` |
| 路径 | `/user/profile` |
| 查询参数 | `?id=100` |
| 片段 | `#basic` |

### 2. 源是什么

源由三部分组成：

```text
源 = 协议 + 主机名 + 端口
```

上面的 URL 对应的源是：

```text
https://www.example.com:443
```

路径、查询参数和片段不参与同源判断。

因此：

- URL 回答“具体访问哪个资源”。
- 源回答“这个资源来自哪个来源”。
- 同一个源下面可以有很多不同的 URL。

### 3. 源不等于网站

例如：

```text
网页：https://www.ctfhub.com
API：https://api.ctfhub.com
```

它们的主机名不同，因此属于不同的源；
但从业务上看，它们仍然可以共同组成 CTFHub 这个网站。

反过来，同一个源的不同路径下，也可能部署多个相对独立的应用。

### 4. URL 不直接包含 HTTP 方法

URL 通常只说明请求目标，不直接声明使用 GET 还是 POST。

HTTP 方法由发起请求的一方决定，并写在请求行中：

```http
POST /User_API/User/Login HTTP/1.1
Host: api.ctfhub.com
```

发起请求的一方可能是：

- 浏览器地址栏导航或普通链接，通常发起 GET；
- HTML 表单，可以配置 GET 或 POST；
- 网页中的 JavaScript，可以发起 GET、POST 等请求；
- Python、Postman 等其他程序。

因此，不能只根据地址栏中的 URL 判断实际请求方法。

## 六、HTTP 协议

HTTP 的全称是超文本传输协议。
它规定了客户端和服务器如何交换网页、JSON、图片和其他数据。

现代网站中，HTTP 不仅用于传输 HTML，也经常用于传输 API 数据。

### 1. 请求—响应模型

```text
客户端                         服务器
  │                              │
  │ ────────── HTTP 请求 ───────→ │
  │                              │
  │ ←───────── HTTP 响应 ──────── │
```

客户端可以是浏览器，也可以是 Python 程序、手机 App 等。

### 2. 请求结构

一次 HTTP 请求主要包含：

```text
请求行：方法、路径、HTTP 版本
请求头：Host、Content-Type 等附加信息
请求体：本次提交的数据，可以为空
```

本次登录请求的简化形式：

```http
POST /User_API/User/Login HTTP/1.1
Host: api.ctfhub.com
Content-Type: application/json

{
  "account": "已省略",
  "password": "已省略",
  "captcha": "已省略"
}
```

其中：

- `POST`：请求方法。
- `/User_API/User/Login`：接口路径。
- `HTTP/1.1`：协议版本。
- `Host`：目标服务器。
- `Content-Type`：请求体格式。
- JSON：实际提交的登录数据。

对应的完整 URL 是：

```text
https://api.ctfhub.com/User_API/User/Login
```

### 3. 响应结构

响应主要包含：

```text
状态行：HTTP 版本和状态码
响应头：响应格式等附加信息
响应体：服务器返回的实际内容
```

本次响应的简化形式：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "status": true,
  "msg": "登录成功"
}
```

`200 OK` 表示服务器正常返回了 HTTP 响应。
`status: true` 表示本次业务处理成功。

两者不是同一个层次，HTTP 200 不一定代表业务成功。
服务器也可能用 HTTP 200 返回“密码错误”。

### 4. 常见状态码

| 状态码 | 常见含义 |
|---|---|
| 200 | 请求得到正常响应 |
| 301、302 | 重定向到其他地址 |
| 400 | 请求格式或参数有问题 |
| 401 | 缺少身份认证或认证无效 |
| 403 | 服务器理解请求，但拒绝访问 |
| 404 | 找不到目标资源 |
| 500 | 服务器内部处理出错 |

### 5. HTTP 无状态

HTTP 协议本身不会自动记住用户是谁，也不会自动记住上一次请求。

网站通常通过以下机制额外维护登录状态：

- Cookie；
- Session；
- Token。

后续请求携带登录凭证，服务器根据凭证识别用户。

## 七、GET、POST 和 OPTIONS

| 方法 | 常见用途 | 数据常见位置 |
|---|---|---|
| GET | 获取页面或数据 | URL 查询字符串 |
| POST | 提交数据，让服务器处理 | 请求体 |
| OPTIONS | 查询通信选项；在 CORS 中可用于预检 | 视具体请求而定 |

这些只是常见用法，不是绝对限制。
POST 的 URL 中也可以有查询参数。

### 1. POST 不等于加密

POST 只是请求方法。
即使参数不显示在地址栏，也不代表参数已经加密。

没有 HTTPS 时，POST 请求体仍可能被中间人读取。

### 2. OPTIONS 不是“检查服务器是否在线”

OPTIONS 的本义是询问目标资源的通信选项。

在 CORS 跨域场景中，浏览器可能先自动发送 OPTIONS，
询问服务器是否允许特定来源、请求方法和请求头。

因此，“预检请求”是 OPTIONS 在特定场景中的用途，
不是 OPTIONS 单词的直接翻译。

## 八、同源、跨域和 CORS

### 1. 什么是同源

协议、主机名和端口必须全部相同，才属于同源。

假设当前网页为：

```text
https://www.example.com/home
```

| 目标地址 | 是否同源 | 原因 |
|---|---|---|
| `https://www.example.com/user` | 是 | 只有路径不同 |
| `http://www.example.com/user` | 否 | 协议不同 |
| `https://api.example.com/user` | 否 | 主机名不同 |
| `https://www.example.com:8443/user` | 否 | 端口不同 |

### 2. 为什么需要同源策略

同源策略是浏览器的安全机制，
主要用于限制一个来源的网页脚本随意读取另一个来源的数据。

例如，恶意网页不应该因为用户打开了它，
就能随意读取用户在其他网站中的账户信息。

需要注意：

- 同源策略不等于所有跨域请求都无法发送。
- 有些请求能够发送，但浏览器不允许脚本读取响应。
- Python、Burp 等程序不受网页 JavaScript 同源策略的同样限制。

### 3. CORS 是什么

CORS 是服务器向浏览器声明跨域许可的一套机制。

服务器通过响应头说明：

- 允许哪些来源；
- 允许哪些方法；
- 允许哪些请求头。

例如：

```http
Access-Control-Allow-Origin: ...
Access-Control-Allow-Methods: POST, GET, OPTIONS
Access-Control-Allow-Headers: ...
```

### 4. OPTIONS 预检过程

对于某些需要预检的跨域请求：

```text
网页准备发起跨域请求
        ↓
浏览器先发送 OPTIONS
        ↓
服务器通过 CORS 响应头说明许可
        ↓
浏览器判断是否继续发送正式请求
        ↓
正式发送 GET 或 POST 等请求
```

本次 CTFHub 登录中：

```text
网页源：https://www.ctfhub.com
API 源：https://api.ctfhub.com
```

主机名不同，因此属于跨域。
浏览器在正式登录 POST 前，先发送了 OPTIONS 预检请求。

## 九、HTTP 与 HTTPS

### 1. HTTP

HTTP 本身不提供传输加密。

如果中间人能够截获普通 HTTP 通信，可能读取或修改：

- URL；
- 请求头；
- Cookie；
- 登录参数；
- 响应内容。

HTTP 默认端口是 80，但也可以使用其他端口。

### 2. HTTPS

HTTPS 可以理解为：

```text
HTTPS = 在 TLS 安全通道中传输 HTTP
```

HTTP 请求方法、请求头、请求体、状态码等仍然存在，
只是通过 TLS 安全通道传输。

HTTPS 默认端口是 443。

### 3. HTTPS 提供的保护

- 加密：防止通信内容被直接读取。
- 完整性保护：发现传输过程中的篡改。
- 服务器身份认证：通过证书和 CA 体系检查服务器身份。

HTTPS 保护的是传输过程，不代表网站本身没有漏洞。
SQL 注入、越权、弱密码等问题仍然可能存在。

### 4. HTTPS 的简化建立过程

```text
浏览器解析 URL
    ↓
与服务器建立网络连接
    ↓
进行 TLS 握手
    ↓
服务器提供证书，浏览器验证
    ↓
建立 TLS 安全通道
    ↓
在通道中传输 HTTP 请求和响应
```

## 十、Burp 的抓包与 HTTPS 代理

### 1. Intercept off

请求经过 Burp 时被记录，然后自动转发。

```text
浏览器 → Burp 记录 → 服务器
```

Intercept off 不等于停止抓包，
请求仍然可以在 HTTP history 中查看。

### 2. Intercept on

请求暂停在 Burp 中，等待用户操作。

- Forward：放行请求。
- Drop：丢弃请求。

如果浏览器一直转圈，可能是请求正在 Burp 中等待处理。

### 3. HTTP history

HTTP history 用于查看已经经过 Burp 的请求和响应。
本次最终就是在这里找到了真正的登录 POST 请求。

### 4. Burp 为什么能看到 HTTPS 内容

正常 HTTPS：

```text
浏览器 ←──── 一条 TLS 安全通道 ────→ 服务器
```

使用 Burp 后：

```text
浏览器 ←─ TLS 连接 1 ─→ Burp ←─ TLS 连接 2 ─→ 服务器
```

本机浏览器信任 Burp 的 CA 证书后，
Burp 分别与浏览器和服务器建立 TLS 连接。

数据到达 Burp 时会被解开，因此 Burp 能看到 HTTP 明文。
这不是破解 HTTPS，而是用户主动信任了一个中间代理。

### 2. 五段式复盘

#### 现象

最初没有看到登录参数，因为选中的是：

```http
POST /User_API/User/getCaptcha
```

它的请求体只有 `{}`，用于获取验证码。

另外还看到：

```http
OPTIONS /User_API/User/Login
```

它是预检请求，不是实际提交登录参数的请求。

#### 假设

真正的登录数据应该由另一个 POST 请求提交。

#### 验证

完成验证码并登录，在 HTTP history 中找到：

```http
POST /User_API/User/Login
```

随后在请求体中看到登录参数，在响应中看到登录成功结果。

#### 原理

打开登录窗口、获取验证码和提交登录信息是不同的业务动作，
可能对应不同的 HTTP 请求。

不能只看 URL 中是否包含 Login，
还要结合请求方法、请求头和请求体判断。

#### 防御与注意事项

- 只在明确授权的目标上进行测试。
- 笔记和截图不能泄露账号、原密码、Authorization、Cookie 和 Token。
- 客户端处理密码字段不能替代 HTTPS。
- 临时项目关闭后可能丢失记录，重要结果应及时整理到笔记中。

## 十二、关于登录请求中的密码字段

请求中没有直接出现原始密码，密码字段表现为一串十六进制字符。

目前只能确定：

1. 原始密码没有直接出现在该字段中。
2. 该字段可能经过哈希或其他转换。
3. 尚未确认具体算法，不能直接断定它就是一次 MD5。
4. 即使客户端进行了哈希，也仍然需要 HTTPS 保护整个通信过程。

## 十三、当前需要保留的核心印象

1. 浏览器是网页的加载器、显示器和运行环境。
2. URL 是资源地址，源是协议、主机名和端口的组合。
3. URL 不直接包含 GET 或 POST，实际方法要看请求行。
4. HTTP 是请求—响应协议，请求和响应都有各自的结构。
5. HTTP 本身无状态，登录状态通常由 Cookie、Session 或 Token 维护。
6. POST 不等于加密，HTTPS 才负责保护传输过程。
7. 跨域的本质是源不同，不是单纯路径或页面不同。
8. CORS 是服务器向浏览器声明跨域许可的机制。
9. OPTIONS 预检是在正式请求前询问许可，不是测试服务器是否在线。
10. Burp 能查看 HTTPS 明文，是因为它是受本机信任的中间代理。
